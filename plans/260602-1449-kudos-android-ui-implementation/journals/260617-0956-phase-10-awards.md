#### Issue 4: CRITICAL RENDER BUG — Trophy Rendered as White Box (SILENT FAILURE)

**Symptom**: Emulator screenshot showed trophy area as a solid WHITE rectangle (160×160). No error logs; no crash; silently wrong.

**Found code**:
```kotlin
Image(
  painter = painterResource(id = award.trophyImageId),
  contentDescription = "Trophy: ${award.name}",
  modifier = Modifier.size(160.dp),
  colorFilter = ColorFilter.tint(Color.White, BlendMode.Screen)  // <-- BUG
)
```

**Root cause**: `BlendMode.Screen` is a **lighten** blend mode. Formula: `screen(C, pixel) = 1 - (1 - C) * (1 - pixel)`. For white (C = #FFFFFF = 1.0):
```
screen(white, pixel) = 1 - (1 - 1.0) * (1 - pixel)
                     = 1 - 0
                     = 1.0 (pure white, always)
```

So `ColorFilter.tint(Color.White, BlendMode.Screen)` **always produces white**, regardless of input pixel. This is a mathematical identity, not a tint.

**Why agent added it**: Likely attempted to "brighten" the trophy or add a glow effect. But used wrong blend mode + wrong base color.

**What should happen**: The composited PNG assets already bake the gold color + glow. No filter needed.

**Fix**: Removed the ColorFilter entirely:
```kotlin
Image(
  painter = painterResource(id = award.trophyImageId),
  contentDescription = "Trophy: ${award.name}",
  modifier = Modifier.size(160.dp)
  // No colorFilter
)
```

Emulator screenshot after fix: trophy rendered correctly (gold ring with per-award name).

## The Brutal Truth

This phase exposed a critical but useful lesson: **background implementer agents produce working UI code that VISUALLY validates on emulator, but has silent bugs that only show in pixel-perfect inspection.**

The white-box trophy bug is the worst offender. The agent:
- Ran visual validation (emulator screenshot)
- Confirmed "trophy visible" on screen
- Reported DONE with "visual validation passed"

But the "trophy" was a **solid white rectangle**, not the intended gold ring. The agent's visual validation loop checked "is something rendering at position X?" not "does it match the design?". This is a category error: **visual validation ≠ pixel-accurate validation.**

Lessons from this:
1. **Visual validation is binary (pixel exists / doesn't exist); design validation is continuous (does it match the intended look).** We need both. The agent had binary; I did continuous (manual side-by-side comparison with design frame).

2. **BlendMode.Screen is a footgun for "tinting" assets.** It's mathematically a lighten operation, not a tint. If you want to brighten, use `BlendMode.Plus`. If you want a hue shift, use a shader. For pre-baked assets, use no filter. Added note to code standards: `.claude/standards/composable-image-rendering.md`.

3. **Stale APK is a silent failure mode.** The old APK rendered old UI; easy to miss that it's outdated instead of concluding "code doesn't work." Solution: script that checks APK install date vs code modification time, warn if mismatch. Or always use `installDebug` for visual validation. Added to Phase 10 phase file.

4. **Trust but verify background agents.** The agent reported DONE; code compiled; tests passed. But 4 real defects (1 critical) existed. This is not the agent's fault — it's a process gap. Background agents need a **merge-gate review** before integration, not after. Phase 10 did the review; all 4 issues caught. Phase 11+ should enforce this earlier (before Track B integration starts).

What's maddening: The code looked **correct** when I read it. The bug was domain knowledge (ColorFilter.tint + BlendMode.Screen = white). I only caught it because I mentally ran the blend-mode formula. If I'd just skim-read ("tint the image, ok"), I'd have missed it. This suggests code review needs **domain experts**, not just syntax checkers. For UI rendering, someone who knows Compose + blend modes. For API code, someone who knows the protocol. For database code, someone who knows the migration strategy.

### AwardViewModel with Route-Param Decoding
```kotlin
@HiltViewModel
class AwardViewModel @Inject constructor(
  savedStateHandle: SavedStateHandle,
  private val awardRepository: AwardRepository
) : ViewModel() {
  
  // Decode route parameter: "awards?award=excellence" → AwardType.EXCELLENCE
  private val _selectedAwardType = MutableStateFlow<AwardType>(AwardType.SIGNATURE)
  
  init {
    val awardParam = savedStateHandle.get<String>("award") ?: "signature"
    _selectedAwardType.value = AwardType.fromString(awardParam)
  }
  
  val selectedAward: StateFlow<Award> = _selectedAwardType
    .flatMapLatest { type -> awardRepository.getAwardByType(type) }
    .stateIn(viewModelScope, SharingStarted.WhileSubscribed(), AwardMockData.signatureAward)
  
  fun selectAward(type: AwardType) {
    _selectedAwardType.value = type
  }
}
```

## What We Tried

### Approach 1: 6 Separate Award Screens (Rejected)
**Initial design assumption**: 6 Figma frames = 6 separate navigation routes (Screen_Awards_Signature, Screen_Awards_Milestone, ...).
**Result**: Massive code duplication; 6 nearly-identical Composables; difficult to add new awards (multiply by 6).
**Reason for failure**: Misunderstood design intent. Frames are state snapshots, not separate destinations.
**Fix**: Recognized the common layout and made award type a parameter. One AwardsScreen, one route with optional `award` parameter. All 6 awards share identical layout; only data differs.

### Approach 2: ColorFilter.tint for Trophy Enhancement (CRITICAL BUG)
**Initial attempt**: Agent thought ColorFilter.tint(White, BlendMode.Screen) would "brighten" or "glow" the trophy.
**Result**: Trophy rendered as solid white box. No error; no warning; silently wrong.
**Reason for failure**: Domain knowledge gap. ColorFilter.tint uses mathematical blend modes; Screen mode on white always produces white.
**Fix**: Removed filter. Asset PNG is pre-baked with gold color + glow; no additional filter needed. Added code standard to avoid this pattern.

### Approach 3: BottomNavigation Tab Matching Without Regex (BUG)
**Initial attempt**: Used `currentRoute?.startsWith("awards")` to match selected tab.
**Result**: When route was `awards?award=excellence`, `startsWith("awards")` matched but tab highlight flickered/didn't stick (navigation state machine confused).
**Reason for failure**: Route parameter appended to route string; naive string matching didn't account for query syntax.
**Fix**: Used `Regex("awards(\\?.*)?")` to match both base route and parameterized routes. Now tab selection is stable.

### Approach 4: Stale APK Installation During Visual Validation (VALIDATION BUG)
**Initial attempt**: Used IDE's Run button; assumed APK was fresh.
**Result**: First screenshot showed Phase 09 UI (old layout), confusing the validation process.
**Reason for failure**: IDE's Run sometimes caches APK if recent build succeeded. Doesn't force uninstall.
**Fix**: Used explicit `./gradlew installDebug` before running. Added note: "Always use installDebug for integration testing."

### Approach 5: Track A Agent Code Review Post-Merge (LATE CATCH)
**Initial flow**: Merged Track A code immediately; reviewed integration bugs after merge.
**Result**: 4 bugs caught (1 critical) but required rework instead of preventing. Wasted review time.
**Reason for failure**: No merge-gate review. Background agent code was trusted without spot-check before integration.
**Fix**: Added pre-merge review step for Phase 11+. Before Track B integration, read 200 lines of critical Track A code (render logic, ViewModel, data). Catch architectural issues early.

## Root Cause Analysis

1. **ColorFilter.tint + BlendMode.Screen = white (domain knowledge)**: Root cause is incomplete understanding of Compose's ColorFilter API. BlendMode.Screen is a mathematical blend operation (lighten); tinting white with Screen always produces white. Agent attempted enhancement without testing or consulting documentation. Lesson: Color/image rendering requires domain expertise. Code review should include rendering specialists.

2. **BottomNavigation route matching with parameters**: Root cause is navigation routing spec gap. When route has optional parameters, the `currentRoute` string includes the parameter syntax (e.g., `awards?award=excellence`). Simple string matching (`startsWith`) breaks. Lesson: Route matching must use Regex or explicit parameter extraction, not naive string ops.

3. **Stale APK during visual validation**: Root cause is IDE behavior inconsistency. Run button sometimes caches APK; sometimes rebuilds. No explicit install step. Solution: Script or enforce `installDebug` as the standard validation command. Also: add APK install timestamp check to CI.

4. **get_media_files recovery after 7 days of downtime**: Root cause was temporary infrastructure issue (MoMorph API endpoint). Alternative endpoint (`get_media_files`) was unaffected. Lesson: In Phase 09, should have tested multiple asset paths upfront (get_figma_image vs get_media_files vs manual export). Would have identified get_media_files as the stable path earlier.

5. **KV section render order reversed**: Root cause is agent didn't validate layout against design spec frame; only confirmed "content renders". Validation was binary (exists vs not), not design-aligned. Lesson: Visual validation checklist should include: (a) components render, (b) spacing matches (38dp tokens), (c) order matches design frame, (d) colors match theme, (e) accessibility labels present.

6. **Status bar inset missing**: Root cause is agent built for "standard" devices; didn't test on notched emulator. Used hardcoded padding (56.dp) instead of safe area calculation. Lesson: Always test on both notched and non-notched emulator configurations. Use WindowInsets for safe area handling.

## Lessons Learned

1. **Visual validation from background agents is binary; design validation is continuous.** Agent's visual check: "Is a 160×160 pixel rectangle rendering at coordinate X?" Yes → reported valid. But "Does it look like a gold trophy?" No (it was white). We need **design comparison checklist**: thumbnail of design frame + screenshot comparison. Agent could provide both; human does final sign-off.

2. **Domain-specific code review is non-negotiable for image rendering.** ColorFilter + BlendMode is Compose + graphics knowledge. Not something a general code reviewer catches. For Phase 11+, assign rendering specialists (familiar with Compose, canvas, shaders) to review image/animation code. For API code, assign network specialists. Etc.

3. **Route parameter syntax is a common bug vector.** When routes have optional parameters (e.g., `awards?award={award}`), navigation matching must use Regex or explicit extraction. Added to code standards: `.claude/standards/compose-navigation.md` → "Always use Regex or navBackStackEntry.arguments to match routes with parameters. Never use naive string matching."

4. **Background agents should submit code for merge-gate review before integration, not after.** Current process: Agent finishes, we integrate, we review, we fix. Better: Agent finishes, human reviewer spot-checks 200 lines of critical logic (VM, render, data flow), agent fixes, then merge. Prevents finding bugs post-integration.

5. **Stale APK is a silent failure mode; enforce fresh install in validation.** Added to Phase 10 phase file: "Validation checklist: (a) `./gradlew installDebug`, (b) `adb shell pm clear <package>`, (c) launch app, (d) screenshot." This ensures clean state.
